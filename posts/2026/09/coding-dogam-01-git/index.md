# 코딩 도감을 시작하며

개발을 하다 보면
"이건 분명 전에 봤는데…",
"그때 어떻게 해결했더라?" 같은 순간이 자주 온다.

그래서 이 시리즈를 시작했다.
완벽하게 정리된 교과서가 아니라, 내가 직접 마주친 것들을 하나씩 기록하는 도감처럼.

이름은 **코딩 도감**.
앞으로 언어, 에러, 개념, 도구, 삽질까지
개발하면서 마주치는 것들을 하나씩 발견 → 관찰 → 기록해보려고 한다.

첫 번째 대상은,
개발을 시작하면 거의 제일 먼저 만나게 되는 **Git**이다.

---

## 개체 정보

- 이름: Git
- 분류: 버전 관리 시스템
- 출현 빈도: 매우 높음
- 위험도: ⚠️ (개념 없이 쓰면 사고 남)

---

## 처음 만났을 때의 인상

처음 Git을 쓸 때는 솔직히 이런 느낌이었다.

- 왜 이렇게 명령어가 많지?
- add 했는데 왜 안 올라가?
- pull 했더니 왜 터지지…?

그냥

```
git add .
git commit -m "message"
git push
```

이 순서만 외워서 쓰고 있었고,
내가 뭘 하고 있는지는 잘 몰랐다.

---

## 관찰 1 — Git은 "파일 저장소"가 아니라 "기록기"

나중에 알게 된 가장 중요한 점은 이거였다.

Git은 파일을 관리하는 도구가 아니라
변경 사항을 기록하는 도구라는 것.

- commit = "이 시점의 변경 내역을 하나의 기록으로 남김"
- Git은 파일 자체보다 변화의 흐름에 관심이 많다

이걸 알고 나니까
커밋 메시지를 대충 쓰면 안 되는 이유도 이해됐다.

---

## 관찰 2 — add는 저장이 아니다

예전에는 이렇게 생각했다.

- add = 저장
- commit = 업로드

근데 실제로는:

- `git add` → "이 변경을 기록 후보로 올린다"
- `git commit` → "이 후보들을 하나의 기록으로 확정한다"

즉, add는 스테이징이고
commit이 진짜 기록이다.

---

## 관찰 3 — Git과 GitHub는 다르다

헷갈리기 쉬운 부분이지만 정리하면:

- Git: 내 로컬에서 기록을 관리하는 도구
- GitHub: 그 기록을 올려두는 원격 저장소

그래서:

- Git 없이 GitHub ❌
- Git은 혼자 써도 ⭕

---

## 요약 정리

- Git은 변경 이력을 관리하는 도구
- add → commit은 "기록을 확정하는 과정"
- Git과 GitHub는 역할이 다르다
- 개념 없이 쓰면, 언젠가 꼭 사고 난다

---

## 코딩 도감 메모

Git은
처음엔 명령어 게임 같았는데,
알고 보니 시간을 되돌릴 수 있게 해주는 기록 장치에 가까웠다.

아직도 브랜치나 머지는 완전히 익숙하진 않다.
그건 아마 코딩 도감 다음 번호에서 다시 만나게 될 것 같다.
