# 로드맵 / 시리즈 계획

## "코딩 도감" 시리즈 개념

포켓몬 도감처럼, 매 시리즈(`#번호`)는 하나의 기술 "개체"를 다룹니다. 하나의 개체는 여러 주차에 걸쳐 기초부터 실전까지 단계적으로 학습하고, 마지막 주차에서 해당 개체를 "코딩 도감"에 정식 등록하는 형태로 마무리합니다.

> **주차 수는 5주로 고정되지 않습니다.** 아래 각 개체의 주차 표는 그 개체에 맞게 정해진 구체적인 구성이며, 다음 개체를 정할 때마다 학습 곡선에 맞춰 다시 결정합니다. 자세한 기준은 [다음 개체 선정 기준](#다음-개체-선정-기준)을 참고하세요.

사용자(codingnanyong)의 직무는 Data Engineer이며, 이 블로그의 개체 선정은 실무 학습을 겸하는 것을 우선순위로 둡니다. `#01` Git → `#02` Docker → `#03` CI/CD → `#04` Kubernetes까지는 어떤 개발 직군에게나 필요한 공통 기반(협업·컨테이너·자동화·오케스트레이션)이고, 그 이후(`#05`~)는 Data Engineer 실무에 직접 맞닿은 개체(워크플로우 오케스트레이션, 분산 처리·스트리밍, 분석 엔지니어링·웨어하우스)로 이어집니다.

## #02 — Docker (초안 — 5주 제안, 확정 전)

사용자가 다음 개체로 Docker를 지정했습니다. 아래는 Git과 동일한 "기본 → 응용 → 협업/실전" 3단 구조를 따른 제안 커리큘럼이며, 확정 전입니다.

| 주차 | 주제 | 발행 예정일 | Linear | 상태 |
| --- | --- | --- | --- | --- |
| 1주차 | Docker 기본 — 첫 조우 (이미지·컨테이너·Dockerfile) | 2026-10-05 | 미정 | 제안됨 |
| 2주차 | 이미지 빌드와 레이어 (Dockerfile 작성, 캐싱, 멀티스테이지 빌드) | 2026-10-12 | 미정 | 제안됨 |
| 3주차 | 볼륨과 네트워크 (데이터 영속성, 컨테이너 간 통신) | 2026-10-19 | 미정 | 제안됨 |

이 5주 구성이 괜찮은지 확인 후, Linear 이슈(부모 + 표준 서브이슈)와 Notion Sprint를 생성합니다. 실제 진행 중 학습 곡선이 다르게 나오면 주차 수는 조정될 수 있습니다.

## #03 — CI/CD (GitHub Actions) (순서 확정, 커리큘럼·주차 수 미정)

Docker(#02) 다음 개체로 확정. Docker에서 만든 이미지를 빌드·배포까지 자동화하는 흐름이라 Docker 다음 순서가 자연스럽고, Git 시리즈 마지막 주(PR→Review→Merge)와도 바로 이어집니다. 이 저장소 자체의 실제 자동화(Linear/GitHub 연동, PR 정책)를 소재로 쓸 수 있습니다. 주차별 커리큘럼은 아직 논의 전이며, 마찬가지로 5주에 맞출 필요 없이 개체 특성에 맞게 정합니다.

## #04 후보 (검토 중)

- Kubernetes — CI/CD(#03) 다음 개체 후보로 사용자가 고려 중. 아직 확정 아님, 주차 구성은 #03 종료 후 논의. 개념이 많은 만큼 5주를 넘는 구성도 자연스럽게 고려합니다.

## #05 이후 후보 — Data Engineer 실무 트랙 (검토 중)

`#04` Kubernetes까지 이어지는 공통 인프라 기반 위에, Data Engineer 직무에 직접 맞닿은 개체들을 다음 순서 후보로 검토 중입니다. 사용자가 실제 업무에서 Airflow·Kafka·dbt를 사용 중이고, 사내에 PostgreSQL + TimescaleDB 기반 Medallion Architecture를 구현했으며, 인프라를 Docker 기반에서 Kubernetes 기반으로 전환한 실제 경험이 있어 — 이 트랙은 가상의 학습이 아니라 실무 경험을 소재로 쓸 수 있는 구성입니다. 순서·확정 여부·주차 구성은 아직 논의 전이며, 아래는 방향성 메모입니다.

- **워크플로우 오케스트레이션 (Airflow)** — 배치/ETL 스케줄링, DAG 기반 파이프라인 관리. CI/CD·Kubernetes에서 다룬 "자동화·오케스트레이션" 개념을 데이터 파이프라인 맥락으로 잇는 자연스러운 다음 단계.
- **스트리밍 & 메시징 (Kafka)** — 이벤트 기반 아키텍처, 실시간 데이터 수집.
- **분석 엔지니어링 (dbt)** — 변환(T) 계층, 데이터 모델링, 쿼리 최적화.
- **데이터 웨어하우스 아키텍처 — Medallion Architecture (PostgreSQL + TimescaleDB)** — 앞선 개체들(오케스트레이션·스트리밍·변환)을 하나로 묶는 실전 종합 사례. Raw → Bronze → Silver → Gold 계층 설계와 시계열 데이터 특성을 다룹니다.

## #09 이후 폭넓은 후보군 — 실무 적용 경험 있음 (검토 중)

아래 주제들도 모두 검토 중이며, 사용자가 실무에서 실제로 적용해 본 내용을 소재로 다룰 수 있습니다(가상 학습이 아님). 순서·개체 분리 여부·주차 구성은 미정이며, 각 개체를 실제로 초안 작성할 때 구체적으로 어떤 도구를 다뤘는지 다시 확인합니다.

- **저장/웨어하우스 계층** — 데이터 레이크 vs 웨어하우스 vs 레이크하우스 개념, 테이블 포맷(Iceberg/Delta Lake/Hudi), 파일 포맷(Parquet/ORC/Avro), 파티셔닝 & 클러스터링 전략
- **수집/통합 (Ingestion)** — CDC(Change Data Capture), ELT 도구(Fivetran/Airbyte/Singer류), API 기반 수집 파이프라인 설계
- **오케스트레이션 대안/비교** — Dagster·Prefect 등과 Airflow 비교, 데이터 계보(lineage) & 카탈로그
- **품질/테스트/거버넌스** — 데이터 품질 테스트(Great Expectations, dbt test), 데이터 계약(Data Contract), PII 마스킹 & 접근 제어
- **분산/대규모 처리** — Spark(배치), Flink(스트림 처리)
- **SQL/성능 심화** — 쿼리 최적화, 실행 계획 분석, 인덱스 전략, 윈도우 함수 등 SQL 심화 패턴
- **모니터링/운영** — 파이프라인 모니터링·알림(Airflow SLA, Prometheus+Grafana), 장애 대응 & 백필(backfill) 전략
- **인프라/클라우드** — Terraform(IaC), 클라우드 데이터 서비스
- **데이터 모델링** — 차원 모델링(Star/Snowflake Schema), SCD(Slowly Changing Dimension)

## 연도별 예상 커버리지 (추정치, 확정 아님)

발행 주기는 매주 월요일이며, 아래는 각 개체가 5주 구성이라고 가정했을 때의 대략적인 타임라인입니다. `#03`/`#04`의 실제 주차 수가 확정되면 이후 일정은 앞뒤로 밀릴 수 있습니다.

- **2026년 안에 다루는 범위**: `#01` Git(완료/초안 완료, ~09-28) → `#02` Docker(~11-02) → `#03` CI/CD(~12-07, 5주 가정) → `#04` Kubernetes 1~3주차(~12-14~12-28, 5주 가정 시 나머지는 해를 넘김)
- **2027년부터 다루는 범위**: `#04` Kubernetes 마무리(~01-11) → 이후 Data Engineer 실무 트랙(`#05` Airflow → `#06` Kafka → `#07` dbt → `#08` Medallion Architecture on PostgreSQL+TimescaleDB)이 순차적으로 이어짐. 실무 트랙은 개체당 5주를 넘길 수도 있어(특히 마지막 종합 사례) 정확한 완료 시점은 각 개체 확정 시 다시 계산.
- **전체 소재 총량 (추정)**: `#01`~`#08`(확정/제안)이 각 5주라고 가정하면 약 40주(2026-09 ~ 2027-06)가 소요됩니다. 여기에 `#09` 이후 폭넓은 후보군(9개 카테고리)까지 각각 별도 개체로 3~5주씩 다룬다고 가정하면 약 27~45주가 추가되어, **전체적으로 2028년 초~중반까지 매주 발행할 소재가 확보**된 셈입니다(오늘 기준 약 1.4~1.6년 분량). `#09` 이후 카테고리를 몇 개 개체로 나눌지, 일부를 합칠지는 아직 미정이라 실제 총량은 달라질 수 있습니다.

## 다음 개체 선정 기준

- 실무에서 반복적으로 쓰이지만 기초부터 정리할 가치가 있는 기술/도구
- Git처럼 "기본 → 응용 → 협업/실전"의 3단 구조로 자연스럽게 나뉘는 주제
- **주차 수는 5주에 고정하지 않는다** — 개체의 학습 곡선에 맞게 유연하게 정한다 (더 복잡하면 5주 초과도 가능하고, 더 단순하면 5주 미만도 가능하다). #01 Git과 #02 Docker(초안)가 5주인 것은 각 개체에 맞춰 정해진 결과일 뿐, 앞으로의 개체도 5주를 따라야 한다는 규칙이 아니다.
- **사용자의 직무(Data Engineer)와 실제로 맞닿아 있는 주제를 우선한다** — 블로그 작성이 곧 직무 관련 스터디를 겸하도록, 공통 기반(Git/Docker/CI-CD/Kubernetes) 다음부터는 사용자가 실무에서 실제로 쓰는 도구(Airflow, Kafka, dbt, PostgreSQL+TimescaleDB 기반 Medallion Architecture 등)를 우선 후보로 삼는다.
